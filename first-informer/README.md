# Kube Operator

## Deploying the operator in the GNU/Linux VM

* Requirements:
  * docker installed
  * debian 12

### GNU/Linux System Requirements

* Configure system requirements (and reboot the VM):

```bash
cat <<EOF >./sysctl.conf.addon
fs.inotify.max_user_watches=2099999999
fs.inotify.max_user_instances=2099999999
fs.inotify.max_queued_events=2099999999
EOF

# cat ./sysctl.conf.addon | sudo tee -a /etc/sysctl.conf
cat ./sysctl.conf.addon | sudo tee -a /etc/sysctl.d/99.koperator.requirements.conf

sudo reboot -h now

# Test de l'effectivité de la configuration après reboot:

sudo ls -alh /proc/sys/fs/inotify


sudo cat /proc/sys/fs/inotify/max_queued_events
sudo cat /proc/sys/fs/inotify/max_user_instances
sudo cat /proc/sys/fs/inotify/max_user_watches
```

I rebotted the VM


### Build n Locally run

So in the first option, what you can do to run the operator is this:

* You create a fresh kind cluster
* You build the operator binary executable
* you set the KUBECONFIG env var to a valid kubeconfig.
* You run the operator binary outside oof the cluster.

Okay let's do that then.

* Create the fresh kind cluster:

```bash
chmod +x ./utils/cluster/provision.sh
./utils/cluster/provision.sh
```

* You build the operator binary executable : 

```bash
go mod tidy
GOOS=linux GOARCH=amd64 go build -o operator

ls -alh ./operator
```

* Just check you can connect to your fresh kind cluster:

```bash
kubectl get all 
```

* You set the KUBECONFIG env var to a valid kubeconfig, n  You run the operator binary outside oof the cluster:

```bash
export KUBECONFIG=~/.kube/config

./operator
```

Then in another shell session, create a pod in your kind cluster, and you'll see the magic happening int he logs of the operator!
